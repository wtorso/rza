# RZA

[English version](README.md)

RZA — низкоуровневый язык и промежуточное представление с явным временем жизни памяти,
проверяемыми обращениями к ней и управлением выполнением в стиле ассемблера. Исходные файлы
имеют расширение `.rza`. Компилятор `rez3asm` проверяет их и генерирует C23, а оптимизацию и
выбор машинных инструкций выполняет компилятор C.

RZA предназначен для небольших вычислительных ядер, которым нужны фиксированные ограничения
памяти и определённое поведение при ошибках. Это инструмент для явной работы с памятью и
потоком выполнения, а не высокоуровневый прикладной фреймворк. Версия
[0.3.0](https://github.com/wtorso/rza/releases/tag/v0.3.0) — предварительный выпуск; язык и
интерфейсы для встраивания ещё могут измениться.

## Требования

Для сборки из исходников нужны [C3
0.8.5_1](https://github.com/c3lang/c3c/releases/tag/v0.8.5_1) с `c3c` в `PATH`, компилятор
C23 (GCC, Clang, Zig или MSVC на Windows), Bash и стандартные утилиты командной строки. Для
запуска готового компилятора C3 не требуется, но для компиляции его C23-вывода всё ещё нужен
компилятор C. Rust не требуется для сборки или использования компилятора; полный набор тестов
использует `rustc` для сравнительных программ и проверок измерений.

Команды ниже рассчитаны на POSIX-совместимую оболочку. CI также собирает и проверяет проект
на Windows с Bash, Zig и MSVC. Готовые пакеты пока доступны только для Linux x86_64 и Windows
x86_64. Исполняемый файл Windows использует динамическую библиотеку Microsoft C
(`VCRUNTIME140.dll`) и `dbghelp.dll`; статическая библиотека времени выполнения не входит в
пакет.

## Сборка и запуск

Клонируйте репозиторий и соберите компилятор:

```sh
git clone https://github.com/wtorso/rza.git
cd rza
bash build_compiler.sh
```

Скрипт создаёт `./build/bin/rez3asm` на POSIX и `./build/bin/rez3asm.exe` на Windows.
Скомпилируйте и запустите включённый в репозиторий автономный пример:

```sh
mkdir -p build
./build/bin/rez3asm examples/hello.rza --emit-c -o build/hello.c
${CC:-cc} -std=c23 -O2 -pedantic -Wall -Wextra -Werror -I include/rza -I . \
  build/hello.c -o build/hello
./build/hello
```

Ожидаемый вывод:

```text
41
```

Чтобы проверить программу без генерации C, выполните:

```sh
./build/bin/rez3asm examples/hello.rza
```

Для корректной программы компилятор ничего не выводит и завершается со статусом 0. При ошибках
в исходнике он выводит диагностику `VIOLATION` и возвращает 1. Ошибки командной строки и
файлового ввода-вывода возвращают 2.

## Руководство по языку

### Регистры и память

Программа использует шестнадцать 64-битных регистров от `%r0` до `%r15` как битовые
контейнеры. Каждая инструкция определяет, как интерпретируются эти биты. Память организована в
ячейки; RZA-код не обращается к ней через сырые указатели.

Пример выше резервирует одну восьмибайтовую ячейку, читает и записывает её через проверяемую
ссылку и печатает регистр:

```asm
res  acc, field, 8
med  acc_m, acc, field

mov  %r0, 0
store [acc_m + 0], %r0
mov  %r0, 41
load %r1, [acc_m + 0]
add  %r2, %r0, %r1
store [acc_m + 0], %r2
print %r2
ret
```

Основные операции с памятью и временем жизни:

- `field` — корневая рамка, существующая всю программу.
- `cav name, parent` создаёт рамку, владеющую областью памяти фиксированного размера.
- `res cell, frame, size` резервирует инициализированную нулями ячейку в действующей рамке.
- `med ref, cell, frame` создаёт проверяемую ссылку — медиатор. Проверки поколения не
  позволяют устаревшему медиатору обратиться к повторно использованной памяти.
- `decay frame` делает недействительными рамку и всех её потомков. Последующий доступ через
  затронутый медиатор вызывает `FAULT` во время выполнения.
- `raise cell, ancestor` меняет владельца только для статической проверки. Память не
  перемещается, а время жизни исходной рамки не продлевается. Домашняя рамка обязана оставаться
  действующей при любом доступе.
- `casc ... endc` проверяет все входные медиаторы перед выполнением блока. Если вход оказался
  недействительным во время выполнения, весь блок пропускается с `ABORT`; выход — ячейка 8 байт.
- `acasc ... endc` ставит работу в ограниченную кооперативную очередь в порядке поступления.
  `await` обрабатывает очередь и возвращает число успешных задач. Это не параллелизм на потоках
  ОС и не сетевой асинхронный ввод-вывод.

RZA сочетает статическую проверку с определёнными исходами во время выполнения. Статически
обнаруживаемые ошибки владения и постоянный выход за границы вызывают `VIOLATION`.
Недействительные медиаторы, динамический выход за границы, недопустимая арифметика и исчерпание
ресурсов вызывают `FAULT`. Каскад с недействительным входом пропускает тело с `ABORT`. Эти
проверки не доказывают прикладную логику и не охватывают сырые указатели, смещения и времена
жизни, которыми управляет C-хост.

Исполняющая среда использует фиксированные области памяти. После инициализации она не вызывает
`malloc`, `realloc` или `free`.

### Процедуры и контракты доступа

Процедуры начинают работу с обнулёнными регистрами. Значения передаются через ячейки, а не
через регистры параметров или возвращаемого значения. Рекурсия запрещена.

В заголовке процедуры со скобками можно перечислить права доступа к медиаторам:

```asm
proc convert(input_m: ro, result_m: rw):
```

Имена ссылаются на существующие глобальные медиаторы и записи их ячеек. `ro` разрешает чтение,
проверки `probe`, создание представлений и использование входом каскада; `rw` также разрешает
запись. Доступ через неперечисленный медиатор и объявление нового медиатора внутри процедуры с
контрактом являются статическими нарушениями. Локальное представление наследует права источника.
Глобальное представление — отдельный медиатор: перечисление источника не даёт доступа к нему.
Вызывающая процедура обязана предоставить все права, необходимые вызываемой, и не может повысить
`ro` до `rw`, в том числе через цепочку вызовов. Пустой контракт `proc pure():` запрещает доступ
к медиаторам. Прежняя форма `proc name:` не меняется. Контракт содержит не более 64 медиаторов
и полностью стирается до генерации C. Диагностика доступа называет процедуру; ошибка вызова
также называет непосредственно вызываемую процедуру.

### Целочисленные операции

Без суффикса типа `add`, `sub`, `mul`, `inc` и `dec` выполняются по модулю 2^64. Проверяемые
варианты `cadd`, `csub`, `cmul`, `cinc` и `cdec` вместо этого вызывают `FAULT` при знаковом
переполнении. Проверяемая арифметика не обеспечивает прикладные правила вроде неотрицательной
квоты: их нужно проверять отдельно. `shr` — арифметический сдвиг вправо, `ushr` — логический.
Деление на ноль, переполняющие знаковые деление и остаток, а также недопустимый счётчик сдвига
вызывают `FAULT`.

Суффиксы `.i8`, `.u8`, `.i16`, `.u16`, `.i32`, `.u32`, `.i64` и `.u64` выбирают знаковую или
беззнаковую семантику для `mov`, `load`, `store`, `add`, `sub`, `mul`, `inc`, `dec`, `cadd`,
`csub`, `cmul`, `cinc`, `cdec`, `and`, `or`, `xor`, `div`, `mod`, `shl` и `ushr`. Знаковые типы
также поддерживают `shr` и `slt`, беззнаковые — `ult`. Каждая ширина даёт 43 сочетания операции
и типа, всего 172. Недопустимые сочетания отклоняются. `loadb` и `storeb` остаются псевдонимами
только для `load.u8` и `store.u8`.

Типизированные операции читают только младшие 8, 16, 32 или 64 бита регистровых операндов.
Результат знакового типа расширяется по знаку, беззнакового — нулями до 64-битного регистра.
Типизированная запись сохраняет ровно этот младший битовый шаблон; 64-битные значения используют
весь контейнер. Тип load/store обязан точно совпадать с типом поля записи. Нетипизированные
ячейки используют смещения в байтах, типизированные — индексы элементов. Выравнивание полей
равно 2 для 16-битных, 4 для 32-битных и 8 для 64-битных типов. В нетипизированных ячейках
доступ к нескольким байтам может быть невыровненным; используется определённое копирование
(`memcpy` в C23-выводе), а не приведение к указателю на более узкий тип. Доступ к отдельным
байтам выполняется через `unsigned char`. Представление памяти следует порядку байтов целевой
платформы и не является переносимым форматом передачи данных.

Циклическая арифметика выполняется по модулю 256, 65536, 4294967296 или 2^64. Проверяемая
арифметика вызывает `FAULT` вне диапазонов -128..127, -32768..32767,
-2147483648..2147483647 или -9223372036854775808..9223372036854775807 для знаковых операций
и 0..255, 0..65535, 0..4294967295 или 0..18446744073709551615 для беззнаковых. Знаковое
деление округляется к нулю; нулевой делитель и деление минимального знакового значения на -1
вызывают `FAULT` и для деления, и для остатка. Беззнаковые деление и остаток вызывают `FAULT`
только при нулевом делителе. Счётчики сдвига — 0..7, 0..15, 0..31 или 0..63: `shl` отбрасывает
старшие биты, знаковый `shr` заполняет знаковый бит, `ushr` — нули.

Десятичные литералы используют те же знаковые и беззнаковые диапазоны. Любой начальный минус в
беззнаковом литерале, включая `-0`, отклоняется. Диапазоны шестнадцатеричных типизированных
литералов — `0x0`..`0xff`, `0x0`..`0xffff`, `0x0`..`0xffffffff` и
`0x0`..`0xffffffffffffffff`; ведущие нули разрешены. Отрицательная шестнадцатеричная форма
запрещена, кроме непосредственных значений i64, для которых сохраняется прежнее правило
совместимости. Непосредственные счётчики сдвига разбираются по прежним правилам i64, включая
отрицательную шестнадцатеричную форму; отрицательный счётчик вызывает `FAULT` сдвига во время
выполнения. `print` печатает знаковое i64, в том числе для значений u64 выше INT64_MAX.

`crc32c DST, STATE, WORD` обновляет CRC32C над восемью байтами `WORD` в прямом порядке от
младшего к старшему. Начальное и конечное XOR-преобразования задаются явно. Исполняющая среда
использует SSE4.2 при поддержке процессором, а иначе даёт тот же результат через побитовую
реализацию.

### Ограниченные представления

`view DST, SOURCE, OFFSET, LENGTH` создаёт медиатор для поддиапазона существующего медиатора без
выделения памяти и копирования данных ячейки:

```asm
view payload_m, input_m, %r2, %r3
loadb %r0, [payload_m + %r1]
```

Для нетипизированных ячеек смещение и длина задаются в байтах, для типизированных — в элементах.
Каждый операнд может быть константой i64 или регистром. Отрицательные или заведомо
невозможные постоянные диапазоны дают `VIOLATION`; динамические ошибки и недействительный
источник — `FAULT`. Если длина задана константой, она фиксирует границу назначения для
статических проверок даже при динамическом смещении или размере родителя. Динамическая длина
сохраняет проверки границ во время выполнения. Пустые представления допустимы, в том числе на
конце ячейки; вложенные представления не могут расширить родителя.

Представления наследуют владельца, домашнюю рамку, время жизни и проверки поколения источника.
Медиаторы, созданные C-хостом, должны содержать корректно выровненные метаданные и описывать
фактический размер объекта. Исполняющая среда проверяет арифметику и согласованность метаданных,
но не может проверить произвольные ненулевые C-адреса. Выходные ячейки асинхронных каскадов
переиспользуют свои фиксированные восемь байтов при каждой постановке в очередь и увеличивают
поколение соответствующего выделения памяти. Поэтому устаревшие медиаторы и представления не
принимают более позднюю публикацию за прежнюю. Представления создаются на верхнем уровне, в
процедурах и внутри синхронных каскадов.
Локальное представление блока видно только в его каскаде. Тела асинхронных каскадов представления
не создают; обе формы принимают заранее созданные представления как входы.

### Типизированные записи

Плоские записи описывают размеры и выравнивание полей, а также число элементов:

```asm
layout Entry: key:i64, value:i64
res entries, field, Entry[2]
med entries_m, entries, field

mov %r0, 0
mov %r1, 42
store [entries_m + %r0].key, %r1
store [entries_m + %r0].value, %r1
load %r2, [entries_m + 0].value
print %r2
ret
```

Для типизированной ячейки значение после `+` — номер элемента, а не смещение в байтах. Компилятор
вычисляет шаг записи и смещения полей по ширине и выравниванию каждого типа. Для полей i64
допустимы и прежние `load`/`store`, и типизированные `load.i64`/`store.i64`. Для каждого другого
типизированного поля нужен точно соответствующий суффикс, включая `load.u64` и `store.u64` для
u64. Нетипизированные ячейки используют смещения в байтах и не имеют селектора поля.

[Пример ring buffer](examples/ring_buffer.rza) показывает типизированное состояние, массив записей
и арифметику индексов с фиксированной ёмкостью.

## Интерфейс командной строки

```text
rez3asm file.rza [--emit-c | --emit-lib] [-o file.c]
rez3asm --lsp
rez3asm --help
rez3asm --version
```

- Без флага вывода компилятор выполняет только проверку.
- `--emit-c` генерирует автономную C-программу с `main`.
- `--emit-lib` генерирует C-библиотеку без `main` для встраивания в C-хост.
- `-o` записывает C в файл и включает генерацию даже без флага вывода. Без `-o` сгенерированный C
  выводится в стандартный вывод.
- `--lsp` запускает языковой сервер через стандартный ввод и вывод.
- Отдельный `--help` выводит справку и возвращает 0; без аргументов справка выводится в stderr со
  статусом 2. Отдельный `--version` выводит `rez3asm 0.3.0` и возвращает 0.

`build_compiler.sh` создаёт компилятор, но не устанавливает его в `PATH`; вызывайте его по пути
или используйте установщик ниже.

## Установка и готовые пакеты

### Установка для текущего пользователя

Из каталога исходников:

```sh
PREFIX="$HOME/.local" bash install.sh
export PATH="$HOME/.local/bin:$PATH"
```

По умолчанию `PREFIX` равен `/usr/local`; `DESTDIR` поддерживается для промежуточной установки.
Установщик не вызывает sudo. Он копирует компилятор для текущей платформы, оба заголовочных файла
исполняющей среды и лицензию. При компиляции сгенерированного C после установки добавьте
`-I "$HOME/.local/include/rza"` к флагам компилятора C.

Из распакованного готового пакета можно установить компилятор без C3, указав его явно:

```sh
RZA_COMPILER=./rez3asm PREFIX="$HOME/.local" bash install.sh
```

### Архивы с готовыми файлами

Скачайте нужный архив и `SHA256SUMS` со страницы
[релиза 0.3.0](https://github.com/wtorso/rza/releases/tag/v0.3.0), затем проверьте и распакуйте
его. `--ignore-missing` позволяет скачать архив только одной платформы:

```sh
sha256sum --check --ignore-missing SHA256SUMS
tar -xzf rza-0.3.0-linux-x86_64.tar.gz
cd rza-0.3.0-linux-x86_64
./rez3asm --version
```

Архив содержит компилятор для текущей платформы, заголовочные файлы исполняющей среды, исходники,
тесты, измерения и примеры. Быстрый запуск выше также работает из этого каталога. `RELEASE.txt`
записывает версию, полный коммит исходников, целевую платформу, версию C3 и `RZA_DIRTY=0`. Перед
публикацией пакеты собираются в двух чистых копиях репозитория и должны совпадать побайтово.
Контрольные суммы проверяют целостность, но не являются цифровой подписью.

## Сгенерированные программы на Linux ARM64 и RV64

Исполняемый файл `rez3asm` остаётся компилятором, работающим на x86_64-хосте. Его C23-вывод можно
кросс-компилировать для little-endian Linux AArch64 и RV64; сам компилятор C3 на эти архитектуры
не перенесён. Отдельной публичной опции выбора целевой платформы в RZA CLI нет.

Проверенная конфигурация:

- Zig 0.17.1 с Clang 22.1.8 в роли кросс-компилятора.
- `aarch64-linux-musl`: little-endian LP64, статическая musl, внешний sysroot не нужен, запуск
  через `/usr/bin/qemu-aarch64-static` без префикса `-L`.
- `riscv64-linux-musl`: little-endian LP64D, статическая musl, внешний sysroot не нужен, запуск
  через `/usr/bin/qemu-riscv64-static` без префикса `-L`.
- QEMU 11.1.3 и `readelf` для запуска и проверки архитектуры.

Начиная с того же `build/hello.c`:

```sh
zig cc -target aarch64-linux-musl -std=c23 -O2 -static \
  -pedantic -Wall -Wextra -Werror -I include/rza -I . \
  build/hello.c -o build/hello-arm64
qemu-aarch64-static build/hello-arm64

zig cc -target riscv64-linux-musl -std=c23 -O2 -static \
  -pedantic -Wall -Wextra -Werror -I include/rza -I . \
  build/hello.c -o build/hello-rv64
qemu-riscv64-static build/hello-rv64
```

Обе программы печатают `41`. На платформах не x86 пути SSE4.2 и другой специфичный для x86 код
исключаются при компиляции; CRC32C использует переносимую реализацию, проверенную независимыми
известными векторами. Аппаратное ускорение CRC на ARM не заявляется.

Внутренний набор тестов также принимает связанные настройки архитектуры и программы запуска:

```sh
CC="zig cc -target aarch64-linux-musl -static" \
RZA_TARGET_ARCH=aarch64 \
RZA_TARGET_LAUNCHER=qemu-aarch64-static \
RZA_TARGET_LOG="$PWD/build/target-aarch64.exec.log" \
RZA_TARGET_EXPECTED_PASS=192 \
bash run_tests.sh
```

Для RV64 укажите `riscv64`, `riscv64-linux-musl`, `qemu-riscv64-static` и отдельный путь к журналу.
Каждый целевой исполняемый файл централизованно проверяется на ELF64, little-endian и требуемый
идентификатор машины до запуска QEMU. Отсутствие настроек или инструментов — инфраструктурная
ошибка, а не повод для запуска на хосте.

Проверенный целевой запуск имеет `PASS=192` и 1211 зарегистрированных выполнений на каждую
архитектуру. Журнал включает попытки изменения и сокращения программ, поэтому 1211 не является
числом семантических тестов. Он включает четыре дифференциальные проверки целочисленных операций,
каждая с 64 корректными и 64 ошибочными программами, и 75 непосредственных проверок рабочих
программ RZA. Внутренние проверки C3/компилятора, LSP, статической диагностики, повторяемости
генерации, пакетов, сравнений с Rust и времени выполняются на хосте или отдельно; они не
засчитываются как доказательство выполнения на ARM/RV64.

Эти результаты относятся только к кросс-компиляции и проверке в пользовательском режиме QEMU.
Реальное оборудование, платформы big-endian, другие libc/ABI, ARM32, RV32 и кросс-платформенные
ASan/UBSan не проверялись; выводов о производительности нет. Готовые архивы по-прежнему содержат
только компилятор для запуска на x86_64-хосте; файлы компилятора ARM/RV64 не создаются.

## Встраивание в C

Сгенерируйте библиотеку и скомпонуйте её с включённой C-программой:

```sh
./build/bin/rez3asm examples/shop.rza --emit-lib -o build/shop.c
${CC:-cc} -std=c23 -O2 -pedantic -Wall -Wextra -Werror -I include/rza -I . \
  build/shop.c examples/shop_host.c -o build/shop_host
./build/shop_host
```

C-хост завершается со статусом 0 после того, как `rza_boot` выполняет программу shop. Его вывод
совпадает с `examples/shop.expected` и заканчивается `DEAD`: последний `probe` видит уничтоженную
рамку корзины. Библиотека экспортирует `rza_boot`, точки входа процедур, функции доступа к рамкам
и медиаторам, `rza_deref_cell`, `rza_arena_alloc` и `rza_await`.

Версия ABI хоста — 5. Пересобирайте все единицы трансляции C с одинаковыми заголовочными файлами
и сгенерированным кодом. Проверки RZA не делают произвольный C-хост безопасным: хост остаётся
ответственным за собственные указатели, смещения и времена жизни объектов.

`rza_boot` выполняется один раз и возвращает `RzaResult`. Повторный запуск и повторный вход из
обработчика диагностики возвращают `RZA_FAULT_ENTRY_STATE`. Экспортируемые процедуры также
возвращают `RzaResult`; их неявные рамки закрываются и при успехе, и при ошибке, поэтому вызовы
можно повторять. `rza_await` возвращает `RzaAwaitResult` с числом завершённых задач и результатом.
Любой `FAULT` отменяет задачи в очереди и сбрасывает флаги ожидания; выполненные записи
сохраняются, а отменённые выходные ячейки не публикуются.

Автономная программа печатает диагностику и завершается со статусом 1 при `FAULT`. Библиотека
возвращает первый код ошибки и строку без завершения процесса и вывода по умолчанию. Для получения
диагностики установите `rza_set_diagnostic_handler`. Транзакционного отката нет: записи до ошибки
остаются видимыми, а хост обязан восстановить или отбросить прикладное состояние по своим правилам.

## Примеры и редакторы

- [hello](examples/hello.rza): минимальная запускаемая программа.
- [ring_buffer](examples/ring_buffer.rza): ограниченная очередь с типизированным состоянием,
  отклонением операций при переполнении и пустоте, включая циклический переход.
- [shop](examples/shop.rza): переходы состояний и встраивание в C-хост.

Там, где применимо, рядом с примером находится `.expected` с ожидаемым выводом.
[Расширение VS Code](https://github.com/wtorso/rza-vscode) подсвечивает синтаксис, показывает
диагностику, подсказки при наведении, определения, ссылки и контекстное автодополнение через
настоящий языковой сервер. Переименование поддерживает записи, поля, рамки, ячейки, медиаторы и
процедуры, использует правки с версией документа и возвращается только если новая программа
проходит проверку. Поскольку каждый `.rza` — самостоятельная программа, навигация и переименование
работают внутри текущего документа; метки не поддерживаются. Лёгкие режимы для
[Emacs и Neovim](https://github.com/wtorso/rza-editors) подсвечивают синтаксис без компилятора.

## Измерения производительности

На Linux с установленными `rustc` и `objdump` выполните:

```sh
bash bench/run.sh
```

Измерения сравнивают CRC32C, хеш-таблицу, кольцевой буфер, синтаксический анализатор и протокол
на RZA, C и Rust; отдельно измеряются вызовы RZA и асинхронная диспетчеризация. Стоимость
компиляции и выполнения записывается раздельно, дизассемблирование сохраняется.
[Руководство по измерениям](bench/README.md) описывает выбор инструментов, выходные файлы и
границы измерений. Результаты относятся только к записанным машине, инструментам и нагрузке; они
не доказывают универсальное преимущество над C или Rust.

## Текущие ограничения

- Поддерживаются только плоские записи
  `u8`/`i8`/`u16`/`i16`/`u32`/`i32`/`u64`/`i64` и массивы фиксированного размера. Вложенные и
  упакованные записи, объединения, битовые поля и переносимый формат передачи данных не реализованы.
- Числа с плавающей точкой не поддерживаются.
- Нет потоков ОС, сборки мусора, рекурсии, физического перемещения памяти, транзакционного отката
  или сетевых примитивов общего назначения.
- Нет общего интерфейса SIMD или встроенных машинных инструкций и собственного оптимизирующего
  генератора машинного кода. Фиксированная инструкция `crc32c` определяет возможности процессора
  во время выполнения и имеет переносимую реализацию. Остальную генерацию для целевой платформы
  выполняет выбранный компилятор C23.
- Фиксированные ограничения ресурсов явно задаются и не увеличиваются автоматически.
- Статический анализ не доказывает корректность прикладной логики и не делает C-хост безопасным.

## Сборка и проверка

Соберите компилятор и выполните полный набор тестов:

```sh
bash build_compiler.sh
bash run_tests.sh
```

Ожидаемый результат: `PASS=305 FAIL=0` на POSIX и Windows MSVC, `PASS=304 FAIL=0` на Windows Zig.
Проверки корректности измерений требуют `rustc` и запускаются на POSIX и Windows MSVC. Объём
проверок Windows Zig меньше из-за конфликта слабых символов Zig compiler-rt при связывании
статической библиотеки Rust; не маскируйте его через `FORCE:MULTIPLE`. Полный скрипт измерений
`bench/run.sh` работает только на Linux; MSVC запускает проверки корректности и таймера.

Другие поддерживаемые варианты компилятора C:

```sh
CC=clang bash run_tests.sh
CC="zig cc" RUST_CC=clang bash run_tests.sh
CC=cl bash run_tests.sh
```

`CC=cl` выбирает Microsoft `cl.exe` и требует Git Bash внутри x64 Native Tools для Visual Studio
2022 с Windows SDK. `cc.sh` передаёт `/std:clatest`, `/W4`, `/WX` и `/TC`; `clang-cl` — другой
интерфейс компилятора и не заменяет эту проверку. MSVC не предоставляет совместимый с GCC UBSan,
поэтому эти проверки выполняются GCC, Clang и Zig. Windows Zig поддерживается с прежними
проверками UBSan и пакетов.

`RUST_CC` выбирает компоновщик для статических библиотек Rust, но не заменяет компилятор C для
сгенерированного RZA-кода. CI запускает Linux GCC/Clang/Zig, Windows Zig, Windows MSVC `cl.exe`,
целевые задачи Linux AArch64/RV64 в QEMU, а также проверки VS Code, создания пакетов,
Extension Host и зависимостей, попадающих в готовое расширение. Linux Clang дополнительно
запускает полный набор с ASan и UBSan. Linux GCC и оба компилятора Windows также проверяют
воспроизводимые пакеты и промежуточную установку. Процесс публикации поддерживает ручной пробный
запуск и выпуск из тегов версий.

## Структура репозитория

- `src/`: CLI, языковой сервер, модель языка, записи, проверки, генератор C23 и помощники памяти
  компилятора.
- `include/rza/`: публичные заголовочные файлы исполняющей среды C23 с фиксированной памятью.
- `build/bin/`: игнорируемый результат сборки компилятора для текущей платформы.
- `install.sh`: установка компилятора и заголовочных файлов через `PREFIX` и `DESTDIR`.
- `release/`: воспроизводимая упаковка, быстрые проверки и примечания к выпускам.
- `examples/`: небольшие запускаемые примеры и ожидаемый вывод.
- `tests/`: позитивные и негативные проверки, выполнение, ABI, LSP, фаззинг и стиль.
- `tests/reference/`: эталонная реализация проверок на C23 и статическая эталонная программа.
- `bench/`: сравниваемые нагрузки, измерения времени и дизассемблирование.
- `editors/vscode`: расширение VS Code как отдельный подмодуль Git.

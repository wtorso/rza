# RZ3: руководство по чтению и написанию вручную

Версия IR: соответствует rez3check (C89/C3). Одна операция на строку.
`#` — комментарий до конца строки. Пустые строки игнорируются.

---

## 0. Ментальная модель за 60 секунд

Программа на RZ3 — это **летопись дерева владения**. Не поток управления,
не структуры данных, а хроника: что родилось, кому выдано полномочие, что
умерло. Есть ровно четыре вида существ и восемь глаголов:

| Сущность | Глаголы-рождения | Глагол смерти |
|---|---|---|
| Рамка (cavity)  | `frame`            | `leave` (Decay) |
| Ячейка (resonator) | `cell`, `casc`/`acasc` (out), `raise` (переезд) | умирает с рамкой |
| Связь (mediator) | `link`            | умирает с рамкой ячейки |
| Шаг (cascade)   | `casc`, `acasc`    | не живёт: мгновенен (sync) или конечен (async) |

Читать файл = проследить, **кто кого переживает**. Писать файл = сначала
нарисовать дерево, потом записать его летопись сверху вниз.

---

## 1. Грамматика (вся)

```
frame  NAME PARENT            — родить рамку; PARENT='-' = прямой ребёнок field
cell   NAME FRAME             — положить опору в ЖИВУЮ рамку FRAME           [I1]
link   NAME CELL ISSUER       — выдать проход на CELL; ISSUER — владелец
                                ячейки или его предок                        [I2]
casc   NAME L1,L2 > OUT FRAME — sync-каскад: все связи живы на входе;
                                OUT — новая ячейка в рамке FRAME             [I3]
acasc  NAME L1,L2 > OUT       — async-каскад: все связи указывают в field;
                                OUT — новая ячейка в field                   [I3]
raise  CELL FRAME             — переприбить опору к СТРОГОМУ предку          [I4]
leave  FRAME                  — Decay: рамка и всё поддерево мертвы
probe  LINK                   — «жива ли связь?» (мягкая семантика)
read   LINK                   — чтение по связи (жёсткая: DEAD = warn)
```

Полевые правила:
- Имена: без пробелов, регистр значим. Конвенция IR: рамки и ячейки — КАПС
  (`SCREEN`, `CART`), связи — с суффиксом `_М`/`_M` (`CART_M`), каскады — глаголы
  (`LOAD`, `SERVE_PHOTO`). ASM-слой (.rz3a) адаптирует дисциплину к
  ассемблерному стилю: те же роли, нижний регистр (`screen`, `cart_m`).
- Порядок имеет значение: это летопись. `link` раньше `cell` — ошибка.
- `field` существует всегда, объявлять не надо, `leave field` запрещён.

## 2. Четыре правила как таблица «что будет, если…»

| Правило | Смысл | Типичная ошибка новичка | Сообщение чекера |
|---|---|---|---|
| **I1** | Опора кладётся только в живую рамку | `cell` после `leave` этой рамки | `cell in dead frame` |
| **I2** | Проход выдаёт владелец ячейки или его предок | Соседняя рамка выдала чужой проход | `link issued by non-owner non-ancestor` |
| **I3** sync | Каскад стартует, только если все связи живы | Каскад по проходу после `leave` | `sync cascade aborted: dead link on entry` |
| **I3** async | Async держит только связи в field + названный out | Async со ссылкой на экран/запрос | `async cascade holds non-root link` |
| **I4** | Подъём опоры — только вверх по дереву | `raise` в соседнюю ветку | `raise to non-ancestor` |
| структура | Нельзя умереть дважды / убить корень | повторный `leave` | `double leave`, `leave of root forbidden` |

## 3. Как ЧИТАТАТЬ файл .rz3

Приём «три прохода»:

**Проход 1 — дерево.** Читайте только строки `frame`/`cell`, мысленно рисуя
отступы. Вы должны уметь ответить: кто корень каждой сущности, какова её
«высота жизни». Пример:

```
frame SESSION -          # глубина 1 (ребёнок field)
frame SCREEN  SESSION    # глубина 2
cell  CART    SESSION    # опора глубины 1: переживёт SCREEN
```

**Проход 2 — границы.** Читайте только `link` и `casc/acasc`. Каждая связь —
место, где одна рамка трогает другую. Вопрос читателя: «выдано законно?
выдающий — владелец или выше?». Каждый каскад — вопрос: «самая короткоживущая
связь каскада — кто? каскад не может быть дольше неё».

**Проход 3 — смерти.** Читайте только `leave` и `raise`. После каждого `leave`
мысленно перечеркните поддерево и все связи, указывающие в него. Всё, что
должно было пережить этот `leave`, но не пережило, — архитектурная ошибка,
и чекер её поймает на следующем же каскаде.

Контрольный вопрос чтения любого файла: **«нарисуй трассу probe так, будто
чекера нет»**. Если ваши предсказания совпали с прогоном — вы файл поняли.

## 4. Как ПИСАТЬ файл .rz3

**Шаг 1 — дерево на бумаге, до кода.** Нарисуйте рамки и ячейки. Правило
размещения: «ячейка живёт в самой НИЗКОЙ рамке, которая гарантированно
переживает всех её читателей». Сомневаетесь — кладите выше; оптимизировать
вниз всегда успеете через `raise` наоборот (перепроектировкой дерева).

**Шаг 2 — летопись сверху вниз.** Порядок строк = порядок времени:
сначала родители, потом дети; сначала ячейки, потом связи на них; сначала
связи, потом каскады через них. Чекер читает так же, поэтому файл,
написанный «в порядке событий», всегда читается линейно.

**Шаг 3 — связи минимальны.** Выдавайте проход самой узкой аудитории:
`link M CART SESSION` — а не field, если потребитель — сессия. Чем ниже
выдающий в дереве, тем уже полномочие. Это capability-дисциплина в действии.

**Шаг 4 — async только через field.** Если эффект переживает рамку (фон,
отложенная задача) — это `acasc`, его связи и out-ячейка обязаны быть в field,
а потребитель назван. Если потребителя назвать не можете — эффект не должен
быть async; это не ограничение чекера, это диагноз дизайна.

**Шаг 5 — смерти явно и один раз.** Каждая рамка имеет ровно один `leave`.
Написали `frame` — сразу найдите место его `leave`. Если места нет — рамка
лишняя, сливайте с родителем.

**Шаг 6 — прогон чекера до ревью.** `rez3check file.rz3`; exit 0 = файл
можно показывать людям. Ревьюер смотрит дерево (шаг 1), а не строки.

## 5. Рецепты (скопируй и адаптируй)

### 5.1 Экран с переживающим его состоянием («кнопка назад»)
```
frame SESSION -
frame SCREEN  SESSION
cell  UI      SCREEN        # эфемерное: умрёт с экраном
cell  DRAFT   SESSION       # черновик: переживёт экран (владелец выше)
link  DRAFT_M DRAFT SESSION
casc  EDIT    DRAFT_M > VIEW SCREEN
leave SCREEN                # UI мёртв, DRAFT жив — возврат восстановит черновик
probe DRAFT_M               # ALIVE
```

### 5.2 Фоновая задача из короткоживущей рамки
```
cell  QUEUE   field         # потребитель назван и бессмертен
link  Q_M     QUEUE field
frame REQ     -
acasc JOB     Q_M > TICKET  # out — в field; REQ может умереть хоть сейчас
leave REQ
probe Q_M                   # ALIVE: фон работает дальше
```

### 5.3 Плагин с горячей выгрузкой
```
frame HOST    -
frame PLUG    HOST
cell  STATE   PLUG
link  P_M     STATE HOST    # выдал предок владельца — законно
casc  CALL    P_M > RESULT HOST
leave PLUG                  # выгрузка: P_M мёртв атомарно, ABA исключён
probe P_M                   # DEAD
```

### 5.4 Агрегат, поднимаемый вверх по мере созревания
```
frame CONN -
frame REQ  CONN
casc  COUNT  > VIEWN REQ    # родился в запросе…
raise VIEWN  CONN           # …переехал к соединению (I4: строгий предок)
leave REQ                   # VIEWN жив
```

### 5.5 Анти-пример: «а давайте всё в field»
```
cell  TEMP_BUF field        # ПЛОХО: эфемерное в реестре бессмертного
```
Диагноз: field должен грепаться кратко. Если `cell ... field` встречается
чаще, чем раз на подсистему, — это вечный стор под новым именем. Ревью:
«почему это переживает запрос? назови потребителя».

## 6. Частые ошибки и их чтение

| Симптом в чекере | Причина | Лечение |
|---|---|---|
| `cell in dead frame` | ячейка создана после `leave` | поднять создание выше или рамку положить выше |
| `link issued by non-owner` | выдающий — не владелец/не предок | выдавать из владеющей ветки; или поднять ячейку |
| `sync cascade aborted` | каскад после смерти рамки связи | поднять ячейку (`raise` до leave или перенести владельца выше) |
| `async cascade holds non-root` | фон держит ссылку на смертное | перенести цель в field и назвать потребителя |
| `raise to non-ancestor` | подъём вбок/вниз | вбок нельзя: поднимите к общему предку, потом выдайте новый link |
| `double leave` | рамка умирает дважды | у вас две точки Decay — у рамки одна смерть, найдите лишнюю |

## 7. Ограничения ручного формата (честно)

- IR многословен: ~2 строки на одну строку C3. Это формат для ИИ и чекера;
  человек пишет его для прототипов, тестов и спецификаций поведения.
- Нет типов полезной нагрузки: ячейка — это имя+рамка, не `Cart` vs `User`.
  Типы появятся на уровне транслятора (артефакт B), в IR они излишни:
  чекеру важно владение, не содержимое.
- Нет чисел/данных: каскад не «вычисляет», он фиксирует факт пересечения
  границы. Вычисления — в C3/коде, RZ3 — скелет владения.
